# 軽量化・電池消費の調査（2026-11-08）

グラフビューを入れる前に、今のアプリの重さと電池消費の原因を調べた記録。
コードの読み取りと、ブラウザ（デスクトップ Chromium を 375×812 に設定）での計測で確認した。**実機（iPhone）では未計測。**

## 結論

| 順位 | 項目 | 根拠 | 影響 |
|---|---|---|---|
| 1 | Google ドライブ自動同期が**解答のたびに**動く | 計測で確認（解答1回 = 通信3回） | 大（連携 ON のときだけ） |
| 2 | ホーム・設定画面のマスコットの常時アニメ | コード確認。演習画面ではほぼ出ない | 小〜中（ホームを開いている間） |
| 3 | 下部ナビの `backdrop-filter: blur(24px)` が常時表示 | コード確認。GPU 負荷は未計測 | 不明（実機で要確認） |
| 4 | 解答タイマーが 0.1 秒ごとに更新 | 計測で確認 | 小（CPU はほぼ無害、起床回数だけ多い） |
| 5 | 起動時に JS データ約1.8MB を同期読み込み | 計測で確認 | 起動のみ。グラフ追加で増える |

最初の見立て（マスコットのアニメとタイマーが主犯）は、計測で**小さい**と分かった。下の「訂正」を参照。

## 1. Google ドライブ自動同期（最有力）

### 仕組み

- [js/util.js:52](../js/util.js) の `saveJSON` は、保存のたびに `scheduleGoogleDriveAutoSync` を呼ぶ。
- [js/gdrive.js:287](../js/gdrive.js) は、対象キー（成績・苦手・既出など）が変わると、**4秒の待ち**のあとに `syncWithGoogleDrive` を実行する。
- 1回の同期は、次の3通信をする。
  1. ファイル検索（GET）
  2. クラウドの全バックアップをダウンロード（GET）
  3. マージした全バックアップをアップロード（PATCH、`JSON.stringify(..., null, 2)` の整形つき）
- 連携すると自動同期は初期で ON（`autosync !== '0'`）。

### 計測（通信は偽物に差し替え。実際の Google には送っていない）

- 解答の間隔が4秒より長いと、**解答1回につき同期1回、通信3回**。3問解いて9通信で確認した。
- ヘビーユーザーを想定（全単語・全文法を解答済み、記録は実際の形式 `{a, c}`）した場合の1回あたり:
  - アップロード 約 224KB、ダウンロード 約 224KB
  - 主スレッドの処理時間は約 2ms（デスクトップ。スマホでも数十 ms 以内の見込み）
- 1時間に300問解くと、おおよそ 300 回 × 約 450KB = **約 135MB の通信と 900 回のリクエスト**になる。

### 見立て

CPU より**通信（モバイル回線・Wi-Fi の無線の起床）**が電池を食う。連携が ON のスマホでは、これが一番大きい可能性がある。
連携 OFF なら無関係。

### 改善案

- 同期の待ちを「最後の保存から 30〜60 秒」か「演習を離れたとき・画面が隠れたとき」にまとめる。`visibilitychange` で隠れたときの同期はすでにある。
- 検索の通信は、ファイル ID を保存して省く（毎回の検索をやめる）。
- アップロードは整形（`null, 2`）をやめる。
- 変更がなければ送らない。

## 2. マスコットのアニメーション

- 48個の SVG すべてに `animation: … infinite` がある（しっぽ 0.75 秒、まばたき、上下の揺れ）。
- 表示される場所を実測した（既定の iOS テーマ、単語ドリル）:
  - 演習画面で問題を解いている間: **見えているマスコットは 0 個**（すべて `display: none`）。
  - 解答直後: 豆知識の 20px と、バナーの 44px の **2個**。次の問題へ進むまで動く。
  - ホーム・設定: 多数（ホームのガイド、目標、本ごとのタイル など）。
- 主スレッドの負荷を、動く版と静止版（`still/`）で交互に3回ずつ比べた。差は **約 1%**（誤差の範囲）。
- `<img>` 内の SVG アニメの描画負荷（GPU・ラスタ）は、この計測では見えない。実機で要確認。
- すでに `prefers-reduced-motion` で静止版に切り替わる仕組みがある。設定の「省エネ」スイッチに流用できる。

## 3. backdrop-filter（blur）

既定の iOS テーマで、常時表示のものがある。

| 場所 | 値 | 常時表示 |
|---|---|---|
| 下部ナビ `.top-page-nav`（[css/theme-ios.css:126](../css/theme-ios.css)） | blur(24px) saturate(180%) | はい |
| シート `.top-sheet` | blur(32px) | 開いたときのみ |
| ポモドーロの小ピル（[home.css:1291](../home.css)） | blur(18px) saturate(180%) | 動作中のみ |
| オーバーレイ 2 か所 | blur(3〜4px) | 開いたときのみ |

演習画面は静止していることが多く、ナビの下の内容がほぼ変わらないので、負荷は小さい見込み。ただし未計測。

## 4. 解答タイマー（0.1 秒更新）

- [home.js:342](../home.js) で `setInterval(tick, 100)`。表示は 0.1 秒単位（`⏱ 33.6`）なので、更新自体は意図どおり。
- 1回の更新は約 0.06ms（強制レイアウトを含めた上限）。10回/秒でも CPU の約 0.06%。タイマーの有無でスループット差は 0.4%（誤差）。
- 問題は CPU ではなく**起床回数**（10回/秒）。表示を 1 秒単位にするか、更新を 250ms にすれば減らせる。優先度は低い。

## 5. 起動

- デスクトップ（ローカル）で、DOMContentLoaded 48ms、JS ヒープ 11MB、DOM 450 要素。軽い。
- データ JS は約 1.8MB を `<script>` で同期読み込み: `grammar.js` 991KB、`tips.js` 454KB、`words.js` 361KB。
- Service Worker は**ネットワーク優先**（[sw.js:124](../sw.js)）。※初稿では「毎回1.8MBを取りに行く」と書いたが、**誤り**。公開先（GitHub Pages）は `cache-control: max-age=600`、ETag あり、gzip 圧縮（`grammar.js` は 991KB → 約 280KB）なので、10分以内は通信なし、それ以降は小さな再確認（304）で済む。影響は小さい。

## 6. 問題がなかった点

- 画面を点灯させ続ける処理（Wake Lock）はない。
- ポモドーロは時刻基準で、バックグラウンドからの復帰にも対応している。
- 60 秒ごとの日付チェックは軽い。
- 画像は全部で約 400KB。
- 音は鳴らすときだけ生成している。

## 訂正

最初の回答で「マスコットの常時アニメが一番疑わしい」と書いたが、演習画面にはほとんど出ておらず、負荷差も約 1% だった。
「タイマーの 0.1 秒更新」も、CPU 負荷としては無視できる。主犯の候補は、ドライブ自動同期に入れ替わった。

## グラフビューへの含意

- 設計書（`docs/superpowers/specs/2026-10-26-grammar-graph-view-foundation-design.md`）は、SVG と d3-force の物理シミュレーションで描く。
- 規模の見積もり（計測ではなく推定）:
  - 世界一・金の文法だけ（301 問）: ノード約 350、エッジ約 800。
  - 全教材（983 問）: ノード約 1,050、エッジ約 2,500〜3,000。
- d3-force の実測は、外部の CDN からのスクリプト読み込みが許可されず、行えなかった。ローカルにも d3 がない。実装前に `vendor/` へ同梱してから測るのがよい。
- 起動に影響しないよう、グラフ用データとコードは**グラフ画面を開いたときに読み込む**。
- 座標を事前計算すれば、実行時のシミュレーションを省ける。

## 計測の限界

- デスクトップ Chromium で測ったもの。iOS Safari とは別物。
- 主スレッドの時間しか見ていない。GPU・ラスタ・無線は測れない。
- ドライブの通信は偽物に差し替えて数えた（実際の通信時間は含まない）。
- 計測用に書き換えた localStorage は、プレビュー用の一時的な origin（localhost:8766）のもので、元に戻した。アプリの実データには触れていない。

## 次に実機で確かめること

1. スマホの設定画面で、Google ドライブ連携が ON か（「☁️ Google ドライブ自動同期中」と出るか）。
2. 連携を OFF にして同じ時間解いたとき、電池の減りが変わるか。
3. iPhone の「設定 → バッテリー」で、Safari（ホーム画面から開いたアプリ）の使用割合。

## 追記: ロジックの処理時間（重いデータでの計測）

全単語（2,517）・全文法（983）を解答済み、苦手が単語500・文法300の状態で、デスクトップ Chromium で測った。1回あたりの平均。
スマホは数倍〜10倍遅い想定でも、どれも数 ms 以内。**CPU の計算量はボトルネックではない。**

| 処理 | 時間 |
|---|---|
| 1問の描画一式（`renderCurrent`） | 0.22ms |
| 選択肢づくり（`buildOptions`、プール 2,517） | 0.06ms |
| 成績の保存（`recordItemStat`、2,517件を丸ごと保存） | 0.21ms |
| 設定＋続きの保存（`updateFooter` 経由） | 0.12ms |
| 単語の絞り込み（`applyFilters`） | 0.57ms |
| ホーム描画（`renderHomePage`） | 0.93ms |
| 単語の苦手リスト描画（500件） | 1.9ms |
| 文法の苦手リスト描画（300件） | 4.5ms |

DOM 要素数は、苦手リストを描画した状態で約 5,000。

### コードの構造で気になった点（設計）

- `updateFooter`（[js/vocab-drill.js:334](../js/vocab-drill.js) 付近）が、表示更新のたびに設定と続きを保存する。10 か所から呼ばれ、描画と保存が結びついている。
- `saveJSON`（[js/util.js:52](../js/util.js)）が、保存のたびにドライブ同期の予約まで呼ぶ。保存層と同期が直接つながっている。
- 出題の続き（`SESSION_KEY`）は、プールの全 ID（最大 2,517 件）を毎回保存している。
- 保存は 1 問ごとに複数キー（成績・苦手・既出・続き・設定）を、それぞれ丸ごと `localStorage` に書く。
- 選択肢づくりが、毎問プールをフィルタしたうえで全件シャッフルしている（3つ選ぶだけ）。

## 追記: 領域ごとの精査（起動と通信／描画とアニメ／長いリスト）

方針: 機能は減らさず、構造を整えて軽くする。自動同期は OFF にする（アプリ側のスイッチ）。実機ベースラインはユーザーが並行して取る。
この追記は読み取りと計測のみ。コードは未変更。

### 起動と通信

| 項目 | 現状（根拠） | 見立て |
|---|---|---|
| Google Identity Services | `index.html:19` で毎回外部スクリプトを読む（`async defer`）。ドライブ連携の手動同期でも使うが、使わない起動でも毎回読む | 必要になったときに読み込む形にできる。ただし `initGoogleDriveClient` が同期関数で、同期の設計と一緒に直すのが安全。**保存・同期の設計の段階で扱う** |
| Web フォント Nunito | `index.html:9` の外部 CSS（描画をブロックする）。`css/app.css` で英数字にだけ効く（日本語は別フォント） | 自前配信（SW でキャッシュ）にすると、外部通信と描画待ちが減り、オフラインでも同じ見た目になる。フォントファイルの追加が必要 |
| `tips.js`（454KB） | `WORD_TIPS` を使うのは `tipHtml` の1か所だけで、未定義でも動く書き方（`typeof`）になっている | 起動後の空き時間に読み込めば、起動時のパースが減る。変更は小さい |
| Service Worker | ネットワーク優先。公開先のキャッシュ設定により実害は小さい | 現状維持でよい。`data/` と `assets/` だけキャッシュ優先にすれば、再確認の往復が減る（効果は小） |

### 描画とアニメ

- マスコットの SVG は48個すべてに無限ループがあり、合計104か所（1個あたり2〜4か所、周期 0.35〜3.6 秒）。
- 同時に見えている数: ホーム 7個、設定 2〜4個、演習は幅の狭いスマホでは 0個（広い画面はヘッダーの1個）。解答直後に小さな 2個。
- つまりホームを開いている間は、10数か所（7個 × 2〜4か所）が動き続ける。演習中はほぼ動かない。
- 改善案: 無限ループをやめ、数回（例: 3〜4回、約5秒）で止まる指定にする。動く楽しさは残る。SVG は48個あるので、機械的に置き換え、`still/` 版を作る `scripts/make-pomeranian-stills.py` と食い違わないか確認する。
- `filterBtnPulse`（[css/app.css:535](../css/app.css)）も無限ループ。数回で止める。
- `transition: all` が16か所。必要なプロパティだけに絞ると、無駄な再計算が減る（効果は小）。
- 解答タイマーは、表示が変わる瞬間にだけ更新する形に直せる。0.1 秒表示を保つなら、更新を `requestAnimationFrame` に寄せ、画面が隠れたら止める。

### 長いリスト

- 苦手リストは、1件ごとに文字列を連結して `innerHTML` に一括で入れる。単語500件で DOM が約3,000要素、1.9ms。
- 単語の苦手: `RAW_WORDS.find(x => x.w === k)` を件数ぶん繰り返す（線形探索、500×2,517）。文法の苦手も `RAW_GRAMMAR.find` で同じ。
  - 改善案: 起動時に1回だけ Map を作る（文法には `GRAMMAR_BY_ID` がすでにある）。
- 長いリストでは `content-visibility: auto` と `contain-intrinsic-size` を `.weak-item` に付けると、画面外の描画・レイアウトを後回しにできる。CSS だけで済み、見た目と機能は変わらない。現在は未使用。

### 保存の設計（慎重に進める。この段階では精査のみ）

データを失わないことを最優先にする。精査で洗い出すこと:

- 書き込み経路を全部列挙する（`saveJSON` / `localStorage.setItem` を直接呼ぶ箇所）。
- 書き込みを遅らせる（まとめ書き込み）場合の失われ方: タブを閉じる、アプリが強制終了する、iOS が裏でプロセスを止める。
- 復元・バックアップ・ドライブ統合（`applyMergedRecordsToLocal` など）との関係。`replaceRecords` が `saveJSON` を通らないこと。
- 既存のテスト（`tests/backup-extras.test.js` など）が守っている不変条件。
- 変更前後で、保存される中身が完全に同じになることを確かめる比較テスト（ゴールデンテスト）を先に作る。

## 実装記録: 起動と通信（2026-11-08）

### 計測（実装前）

- 公開先と同じ ETag つきのサーバーで再読み込みを3回測ると、毎回 fetch 約48件、`cache.put` 約48件（約0.9〜1.6MB）。中身が変わっていなくても全部書き直していた。
- フォントの CSS（Nunito）は、ローカルの CSS 4本と並んで描画をブロックしていた。
- データ JS のパース・実行は `words.js` / `grammar.js` / `tips.js` それぞれ 1ms 未満（Node）。`tips.js` の遅延読み込みは得るものがないので取り下げた。
- Google 認証スクリプトの遅延読み込みも取り下げた。iPhone では、タップの直後にスクリプトを読み込むとポップアップがブロックされることがあり、連携を使っている場合は効果もない。

### 変更

| 変更 | 内容 | ファイル |
|---|---|---|
| 変わっていないファイルは書かない | 取得した応答の ETag（なければ Last-Modified）をキャッシュ済みのものと比べ、同じなら書かない。どちらも無ければ従来どおり毎回書く。書き込みは `event.waitUntil` で待つ（以前は待たず、途中で Service Worker が止まると失われうる） | [sw.js](../sw.js) |
| フォント CSS をブロックしない | `media="print"` と `onload` で、描画をブロックしない読み込みにした。`<noscript>` に同じ CSS を置いた | [index.html](../index.html) |
