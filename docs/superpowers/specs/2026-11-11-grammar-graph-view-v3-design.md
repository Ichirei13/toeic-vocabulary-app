# 文法グラフビュー v3 設計（苦手が位置と量で見える・近い問題を解く）

日付: 2026-11-11 / 状態: **実装済み（2026-11-12。実装計画 docs/superpowers/plans/2026-11-11-grammar-graph-view-v3.md、実機（iPhone）の確認は未実施）**

`2026-11-08-grammar-graph-view-v2-design.md`（v2）への追加と変更。v2 のデータの形（§3・§4）、理解度の計算（§6）、
入口（§8）は引き継ぐ。変えるのは **配置の方式（v2 §2-1・§5）、線の描き方と LOD（v2 §7）、操作（v2 §7）** と、
v2 が対象外にしていた **グラフからの出題**。

## 1. 目的

v2 のグラフは、ノードが並んでいるだけに見える。原因は次の 3 つ。

1. 苦手が位置に効いていない（座標は全員共通で、記録は色にしか出ない）。
2. 苦手の量が見えない（色は赤かそうでないかだけ。全体表示では線も本と章の間にしか出ない）。
3. 周辺をたどる操作がない（タップしても詳細シートが出るだけ）。

この版で、次の 3 つができるようにする。

- **全体を見て、どの概念・ひっかけ・章に苦手が偏っているかがわかる**（開いた瞬間に、位置・大きさ・線の太さで読める）。
- **ノード 1 つから、その周辺が見える**（タップでつながる先が浮かび上がる）。
- **「これに近い問題を 30 問解く」ができる**（どの種類のノードからでも）。

### 利用者が決めたこと（2026-11-11）

| 内容 | 決定 |
|---|---|
| 配置 | 開いたときに 1 回だけ力学を回して止める。毎回同じ位置である必要はない |
| 重さ | グラフビューは見ている時間が短いので、開くときの処理は多少重くてよい |
| 近さ | 同じひっかけ・共有する概念の数を重く数え、本をまたぐ |
| 30 問の選び方 | 苦手・未解答を優先し、足りなければ正解済みで埋める。問題数は 30 |
| 起点 | どの種類のノードでもよい |
| 力学の実装 | d3-force を同梱し、ビルド済みの座標から続きを回す |
| 線 | ズームしなくても線が見えるようにする |

### 守ること

- 起動時の読み込みを増やさない（起動のリクエスト数 48 件のまま。追加ファイルはグラフを開いたときだけ読む）。
- オフラインで動く。
- 学習記録（正誤・苦手リスト）、バックアップ、Google ドライブ同期の形式を変えない。
- 力学が収まった後と、移動のアニメーションが終わった後は、v2 と同じく入力があったときだけ描く（タイマーなし、常時ループなし）。
- 既存の単語ドリル・文法ドリルの通常の動作と、保存内容（比較用テスト）を変えない。

### やらないこと

- ノードを指でつかんで動かす操作（動き続ける力学が要る）。
- ドリルの解説画面に概念・ひっかけを出す（別の設計にする）。
- 単語のグラフ。

## 3. 配置（開いたときの力学）

### 3.1 流れ

1. ビルド済みの座標（`data/grammar_graph.js` の `x`・`y`）で、すぐに 1 回描く。
2. 記録から理解度（`src/mastery.js`）を計算し、`src/graph-force.js` で力を組み立てる。出発点はビルド済みの座標。
3. 1 フレームあたりの計算時間に上限（8 ミリ秒。`SETTLE_BUDGET_MS`）を付け、`requestAnimationFrame` ごとに回せるだけ回して描く。
   ノードが動いて収まる様子が見える。
4. 決めた回数（120 回。`GRAPH_RUNTIME.ticks`。下の実測で決めた）に達したら止める。座標を確定し、タップ用の格子索引を作り直す。
5. 以後は入力があったときだけ描く。

計測（2026-11-11、Mac の Node、1,201 ノード・3,180 エッジ、今のビルドの力）: 400 回 約 1.2 秒、200 回 約 0.6 秒、120 回 約 0.4 秒。
iPhone では未計測。

実装後の計測（2026-11-12、デスクトップの Chromium、**CPU 4 倍の制限**、苦手 110 問 = 全体の約 1/9、120 回。iPhone では未計測。`tests/graph-view.test.js` の「性能: 力学」が記録する）:

| 画面 | 収まるまで | 1 フレームの最長 | 全体表示 1 回の描画 |
|---|---|---|---|
| 375×812 | 約 2.4 秒（2448 ms） | 33 ms | 0.8 ms |
| 1280×800 | 約 2.9 秒（2940 ms） | 32 ms | 0.9 ms |

どちらも 3 秒以内で、回数は 120 のまま変えていない。1 フレームの最長が 8 ミリ秒の上限を超えるのは、
CPU を 4 倍遅くしているため（1 回の tick が上限より長くなると、1 回は必ず回す）。

### 3.2 力

`src/graph-force.js` は、d3-force の関数（`forceSimulation` など）を引数で受け取る。ビルド（Node）とアプリ（`window.d3`）の両方から使うため。

- **ビルド時**（記録なし）: v2 と同じ力。生成物 `data/grammar_graph.js` は 1 バイトも変わらないこと（変わる直し方は採らない）。
- **実行時**（記録あり）: ビルド時の力に、次の違いを足す。
  - 苦手・復習期限の問題: 親（章・ルール）への結びつきを弱め、つながる概念・ひっかけへ強く引く。ひっかけは概念より強く引く。
  - それ以外の問題: ビルド時と同じ。本・章の塊に残る。
  - 概念・ひっかけ: 中央寄りのまま。衝突半径を、配下の苦手の数に応じて広げる（集まった問題が重ならないように）。
- 乱数の種を固定する。同じ座標・同じ記録から回すと同じ配置になる。
- 係数は `src/graph-force.js` の `GRAPH_RUNTIME` にまとめた。スクリーンショットで確かめた結果、初期値のまま変えていない:
  `ticks` 120、`alpha` 0.3、`weakParentFactor` 0.25、`weakAnchorFactor` 0.2、`weakConceptStrength` 0.5、`weakTrapStrength` 0.8、
  `weakLinkDistance` 46、`hubCollidePerWeak` 3。`GRAPH_LAYOUT` は生成物が変わるので動かさない。

### 3.3 細かい決め

- 収まるまでの間、パンとズームはできる。タップは収まってから受け付ける。
- 記録が変わったとき（`GraphView.refresh`）は、色・大きさ・線だけ更新する。配置はそのまま。
- 本の絞り込み・「苦手のみ」の切り替えでは、配置を作り直さない。
- 「配置し直す」ボタンを置く。押したときだけ、今の記録で力学をもう一度回す。
- OS の「視差効果を減らす」設定（`prefers-reduced-motion`）が有効なら、途中の動きは描かず、完成形だけ出す（計算は同じく数フレームに分ける）。
- d3-force の読み込みに失敗したら、ビルド済みの固定配置で表示する（v2 の動作。グラフは使える）。
- 画面を離れたら（`destroy`、タブが hidden）、計算の途中でも止めて解放する。hidden から戻ったら続きを回す。

## 4. 線と、苦手の量の表示

### 4.1 束ねた線

v2 では、概念・ひっかけの線はすべて「問題 → 概念 / ひっかけ」で、両端が表示されているときだけ描く。
問題ノードは約 5 倍までズームしないと出ないので、全体表示では本と章の間の線しか見えなかった。

| ズーム | 描く線 |
|---|---|
| 遠景 | 親子の線 + 「章 ↔ 概念 / ひっかけ」の束ねた線 |
| 中景 | 親子の線 + 「ルール ↔ 概念 / ひっかけ」の束ねた線（ルールを持たない問題のぶんは章との線） |
| 近景 | 親子の線 + 問題ごとの線（v2 と同じ） |

- 束ねた線は、その章（ルール）の中でその概念・ひっかけにつながる問題の数から作る。`src/graph-filter.js` の純粋関数で、
  グラフを開いたときに 1 回だけ集計する。苦手の数は `refresh` のたびに数え直す。
- 本数（2026-11-11 の実データ）: 章の束 248 本（うち問題 2 問以下が 112 本、最大 78 問）、ルールの束 477 本（うち 2 問以下が 268 本）。
- **太さ**は、束の中の苦手・復習期限の問題の数で決める。苦手 0 の線は細く薄く、苦手がある線は赤寄りの色で太く描く。
- 遠景・中景では、問題数が少なく苦手が 0 の線（2 問以下。`BUNDLE_MIN_Q`）を省く。
- 太さ（`BUNDLE_WIDTHS`）は苦手 0 / 1〜2 / 3〜5 / 6 以上で 0.8 / 1.3 / 1.8 / 2.4 px。苦手のある束の不透明度は 0.5（`BUNDLE_WEAK_ALPHA`）。
  苦手が 110 問あると中央に束が集まって塗りつぶしになったので、最初の案（3.8 px まで・不透明）より細く薄くした。

### 4.2 苦手の問題は、どの倍率でも出す

苦手・復習期限の問題は、遠景・中景でも小さな点で描き、概念・ひっかけへの線も描く。
力学で概念・ひっかけのまわりに集まるので、全体表示で「どこに溜まっているか」が見える。それ以外の問題は v2 と同じく近景だけ。

### 4.3 ノードの大きさ・色・数

- **大きさ**: 概念・ひっかけ・章・ルールは、配下の苦手・復習期限の問題数に応じて大きくする（`1 + min(1.2, 0.25 × √苦手の数)` 倍。0 のときは v2 の大きさ）。
- **色**: v2 の 6 つの状態（未解答・期限・苦手・少ない・良い・中間）はそのまま。赤（期限・苦手）だけ、配下に占める苦手の割合で
  3 段階の濃さにする（1 割未満 / 3 割未満 / それ以上）。
- **数**: 苦手があるノードは、ラベルの横に数を出す（例: 「受動態 12」）。
- **問題のラベル**: 問題ノードの番号ラベル（#1152 など）は近景だけ。遠景・中景では置かない。
- **凡例**: 画面の隅に小さく出す（大きさ = 苦手の数、赤の濃さ = 割合）。

## 5. タップしたときの表示

ノードをタップすると、つながる先を通常の濃さで描き、それ以外を薄くする。詳細シートは v2 と同じく開く。

| タップしたノード | 浮かび上がるもの |
|---|---|
| 問題 | その問題の概念・ひっかけ・ルール・章と、近い問題の上位 30 問（§6 の点数） |
| 概念・ひっかけ | 配下の問題すべてと、それらが属する章 |
| ルール・章・本 | 配下の問題と、それらがつながる概念・ひっかけ |

- 浮かび上がった問題は、どの倍率でも点として描く。番号ラベルは、遠景・中景では 6 個まで（`FOCUS_Q_LABELS`。選択した問題自身は別。概念・ひっかけ・章・ルールのラベルを優先する）。
- 浮かび上がらせる線は太さ 1.8 で描き、ほかの線は薄くする。浮かび上がらせる線が 60 本を超えるとき（`FOCUS_EDGE_MANY`。配下が多い概念など）は、
  扇状に重なって塗りつぶしになるので、太さ 1・不透明度 0.5 にする。
- 背景をタップする、またはシートを閉じると元に戻る。
- 対象の集合は、タップしたときに 1 回だけ計算する（`src/graph-filter.js` の純粋関数）。描画のたびには計算しない。

### 詳細シートからの移動

- ノードをタップしてシートが開いたとき、そのノードがシートに隠れる、またはシートの上端から 40px 以内にあれば（`REVEAL_GAP`）、倍率はそのまま、シートの上の見える範囲の中央へ動かす（同じ 0.3 秒の移動。「視差効果を減らす」では即座）。見えている位置なら動かさない。
- シートの問題一覧で問題をタップすると、その問題の位置へ画面を動かし、選択をその問題に切り替える。
- 移動は約 0.3 秒のアニメーションで、終わったら必ず止める。`prefers-reduced-motion` が有効なら、アニメーションなしで切り替える。
- **シートは背景を覆わない下部パネル**にした（実装計画「設計書からの変更点」1）。v2 のシートは覆い（`.graph-sheet-backdrop`）がグラフ全体を塞ぎ、開いている間はパンもズームもできず、周辺を見て回れなかったため。
  既定は画面の 42% の高さで開き、「広げる」で 72% にする。閉じるのは ×・Esc・何もない場所のタップ。上の「移動のときは半分に縮める」は、この形に含まれる。
- **苦手が 1 問もないときは力学を回さない**（同 2）。記録なしの力はビルド時と同じで、回しても少し揺れるだけなので、固定配置のまま出す。

## 6. 近さの計算（`src/graph-near.js`）

**入力**: グラフ、起点のノード、問題ごとの記録（苦手・期限・解答数）、問題数（既定 30）。
**出力**: 出題する問題 id の並びと、各問題の点数。DOM にも保存にも触れない。

1. **起点の問題を決める。** 問題ノードならその 1 問。それ以外は配下の問題すべて（`members`）。
2. **起点の特徴を作る。** 起点の問題が持つ概念・ひっかけ・ルール・章を数え、割合にする。
3. **候補に点数を付ける。** 起点と共有する特徴ごとに「重み × 起点での割合」を足す。

   | 特徴 | 重み |
   |---|---|
   | 同じひっかけ | 最も重い |
   | 同じ概念 | つながる問題が少ない概念ほど重い |
   | 同じルール | 中くらい |
   | 同じ章 | 軽い |

   概念につながる問題数には大きな差がある（実データ: 最多 300 問、最少 29 問。ひっかけは 5〜54 問）。
   概念の重みは問題数の逆数の対数で決める。概念を多く持つ問題が有利になりすぎないよう、候補が持つ特徴の数で割って調整する。
   重みの具体値（同 4）: ひっかけ = 2 × ln(1 + 全問題数 / つながる問題数)、概念 = 1 × 同じ式、同じルール = 1.5、同じ章 = 0.3。概念・ひっかけの点数は、候補が持つ概念・ひっかけの数の平方根で割る。定数は `src/graph-near.js`。
4. **選ぶ。** 候補は「近い順の上位（問題数 × 3 = 90 問）∪ 起点の配下の問題」（概念や本が起点のとき、配下の苦手が 90 問の外に落ちるため。実装計画「設計書からの変更点」3）。その中から次の順に埋める。同じ区分の中では近い順。
   1. 苦手・復習期限の問題
   2. まだ解いていない問題
   3. 正解できている問題
5. **並べる。** 起点が問題ノードなら、その問題を先頭にする。残りは混ぜる（混ぜる乱数は引数で受け取る。テストでは固定する）。

候補が 30 問に届かないときは、ある分だけ返す。

## 7. 近い問題の出題

- 詳細シートに「近い問題を N 問解く」ボタンを置く（N は実際に出る数。最大 30）。どの種類のノードでも出す。
- 押すと、`js/grammar-drill.js` の `startGrammarCustomDrill(ids, label)` が、問題の配列を `state.grammarPool` に入れ、
  演習ページへ移る。採点、苦手の記録、復習の間隔は今の仕組みをそのまま使う。
- 演習画面の上に「〈起点の名前〉に近い N 問」と「解除」を出す。解除する、またはフィルターを変えると、通常の出題に戻る
  （通常の出題の続きが残っていれば、そこから再開する）。
- 解き終えたら、完了画面に「グラフに戻る」を出す。

### 保存（設計の会話からの変更点）

設計の会話では「出題の続きの記録にラベルの項目を足す。その記録がバックアップ・同期に含まれていたら、足さない形に切り替える」と決めた。
確かめたところ、**出題の続き（`SESSION_KEY`）は `RECORD_KEYS` に入っていて、バックアップにも Google ドライブ同期のファイルにも含まれる。**
そこで次の形にする。

- 近い問題の出題中は、通常の出題の続き（`SESSION_KEY` と、本ごとの `BOOK_SESSIONS_KEY`）を**書き換えない**。
  30 問で通常の続きが上書きされることも、ほかの端末へ同期されることもない。
- 近い問題の出題の続きは、**この端末だけの新しいキー**（`toeic_near_drill_v1`）に保存する。
  中身は `{ ids, index, score, answered, label }`。再読み込みやアプリの切り替え（iOS が PWA を終了させたとき）のあとも続きから解ける。
  解き終える・解除する・フィルターを変えると消す。
- このキーは、バックアップ（`RECORD_KEYS`・`EXTRA_KEYS`）にも同期にも入れない。`BACKUP_FORMAT` は変えない。
- 別のタブへの反映（`CROSS_TAB_KEYS`）にも入れない（出題の続きと同じく、タブごとの画面の状態。`CLAUDE.md` の約束 7）。
- 保存は `saveJSON` / `loadJSON` 経由（`CLAUDE.md` の約束 3）。
- 回答の記録（`grammarStats`・`toeic_weak_grammar` など）は、通常の出題と同じ形で保存される。

## 8. テスト

### 通し続けるもの

- 起動のリクエスト数 48 件、グラフ用のファイルを起動時に取らないこと。
- `tests/storage-writes.test.js`（比較用の保存内容が同一）、`tests/storage-subscribe.test.js`、`tests/data-safety.test.js`。
- `tests/test_file_lists.py`（ファイル一覧の整合）。
- `tests/build_graph.test.js`（生成物の契約。**`src/graph-force.js` へ移す前後で、生成物が同一であること**を足す）。

### 直すもの

- 「動いていないとき `requestAnimationFrame` が 0 回」は、力学が収まった後と、移動のアニメーションが終わった後に測る。

### 足すもの

- 単体（`tests/unit/`）
  - `graph-force`: 同じ入力から同じ配置。苦手の問題が、収まった後に概念・ひっかけへ近づいている（ビルド済みの座標との距離の比較）。記録なしならビルドと同じ力。
  - `graph-filter`: 束ねた線の本数と問題数・苦手数。タップしたときの集合（種類ごと）。
  - `graph-near`: 同じひっかけを持つ問題が、同じ概念だけの問題より上に来る。苦手 → 未解答 → 正解済みの順で埋まる。
    候補が足りないときは少ない数で返る。同じ入力から同じ点数。記録にない問題・グラフにない id でも落ちない。
- ブラウザ（Playwright）
  - 苦手を入れた状態で開くと、収まった後に、苦手の問題が遠景で描かれている。
  - タップで周辺以外が薄くなる。背景のタップで戻る。
  - シートの問題をタップすると画面が動き、選択が切り替わる。
  - 「近い問題を解く」で演習ページへ移り、問題数が合う。解除で通常の出題に戻り、通常の続きが変わっていない。
    再読み込みしても続きから解ける。回答すると苦手の記録が通常と同じ形で保存される。
  - 力学の途中で画面を離れると止まる（リスナー・rAF が残らない）。
  - d3-force の読み込みに失敗しても、固定配置で開ける。
  - オフライン（Service Worker 経由）で開ける。

### 計測

開いてから収まるまでの時間と、収まるまでの 1 フレームの最長時間を記録する。デスクトップの Chromium に CPU 4 倍の制限を付けた値で、
iPhone では未計測と断る。長すぎる場合は回数を減らす。それでも足りなければ、計算を Web Worker に移す案を別に検討する（この設計には含めない）。

## 9. 完成の基準

1. 苦手がある状態で開くと、ズームしなくても、どの概念・ひっかけ・章に苦手が多いかが位置・大きさ・線の太さで読める。
2. どの種類のノードでも、タップするとつながる先が浮かび上がる。
3. どの種類のノードからでも「近い問題を解く」で出題でき、解除すると通常の出題の続きに戻る。
4. 収まった後は描画が止まっている。起動のリクエスト数は増えない。
5. バックアップ・同期の形式と、通常の出題の保存内容が変わらない。全テストが通る（既知の失敗 `tests/next-browser.cjs` を除く）。

## 10. 実装の順序

各段階の終わりで、スクリーンショットを見せて確認を取る。

1. 力の定義を `src/graph-force.js` に移す（生成物が変わらないことを確かめる）。
2. d3-force を同梱し、開いたときに力学を回す。
3. 束ねた線と、苦手の量の表示。
4. タップしたときの表示と、シートからの移動。
5. 近さの計算と、近い問題の出題。
6. 計測と、係数の調整。

公開（`python3 upload.py`）は、`-n` で内容を確認し、利用者の許可を取ってから行う。
