# 文法グラフビュー(基盤)設計

日付: 2026-10-26 / ブランチ: `claude/friendly-bohr-lwlh2r`

## 1. 背景と目的

文法学習の新機能として、複数の参考書の問題を「文法ノード」のグラフでつなぎ、弱点を可視化・出題に生かす構想がある(将来の目標は 30 問診断・章チェックなど)。

今回の対象は、その**最初の一歩であるグラフビューの基盤**に限る。

> 解いた履歴がグラフに反映され、間違えた問題・苦手な分野が赤く見える。

後続の機能(診断、章チェック、類題出題)は別の仕様で扱う。

### 前提と制約(合意済み)

- 静的 HTML のまま作る(サーバなし、ビルドなし)。オフライン動作(`sw.js`)を壊さない。
- スマホ幅を基準に設計し、PC でも使えるようにする。
- 既存の文法ドリル・単語ドリルの画面と動作は変えない。
- 本をまたぐ関連リンクは、ユーザーが Obsidian の vault(md)を提供した後に別途取り込む。今回は md を読まない。
- 授業用テキストなどの追加の本は今回扱わないが、後から足せる形にしておく。

## 2. スコープ

### 含む

1. 既存の問題データから**仮のグラフ**を生成するスクリプトと、その生成物。
2. グラフデータの形式(後から md 由来のものに差し替えても、ビュー側を変えずに済む契約)。
3. ノードの理解度状態を計算する純粋関数と、そのテスト。
4. グラフビュー(SVG 描画、物理配置、ドラッグ、ズーム、タップで詳細シート)。
5. 「学習対象」への「グラフ」の追加。

### 含まない

- md の解析、本をまたぐリンク、授業用テキスト。
- 30 問診断、章チェック、練習ボタンによる出題プールの差し替え。
- バックアップ形式の変更(グラフビューは既存の記録を**読むだけ**で、新しい記録を持たない)。
- 既存の `index.html` の大規模な分割(今回は新規コードを `js/` に置くだけにとどめる)。

## 3. グラフデータの契約

`data/grammar_graph.js` は、グローバル変数 `GRAMMAR_GRAPH` を 1 つ定義する(既存の `data/words.js` / `data/grammar.js` と同じ流儀)。

```js
const GRAMMAR_GRAPH = {
  version: 1,
  nodes: [
    { id, label, kind, book, qids }
  ],
  edges: [
    { s, t, kind }
  ]
};
```

| フィールド | 内容 |
|---|---|
| `id` | 文字列。全体で一意 |
| `label` | 表示名 |
| `kind` | `'root'`(本)/ `'category'`(章)/ `'concept'`(ルール・小テーマ)/ `'question'`(問題) |
| `book` | 本の識別子。`'sekai'` / `'kin'`。将来の本はここに追加する。本をまたぐノードでは `null` |
| `qids` | そのノードの**直接の**問題 ID の配列。`question` ノードは自分の ID 1 つ。`concept` は配下の問題 ID。それ以外は空配列 |
| `edges[].kind` | `'parent'`(階層)/ `'related'`(将来の本をまたぐ関連。今回は出力しない) |
| `edges[].s` / `.t` | 親 → 子(`parent`)。`related` は無向として扱う |

ビューと理解度計算は、この形だけを前提にする。生成元(今回は問題データ、将来は md)には依存しない。

### 仮グラフの生成規則(`tools/build_graph_from_questions.mjs`)

入力は `data/grammar.js` の `RAW_GRAMMAR`。出力は `data/grammar_graph.js`。手元で `node tools/build_graph_from_questions.mjs` を実行して生成し、生成物をコミットする。

- **root**: 本ごとに 1 つ。`id` は `book:sekai`、`book:kin`。
- **category**: 章ごとに 1 つ。`id` は `cat:<book>:<ch>`、`label` は `ch_title`。
- **concept**:
  - 金の文法: ルール番号ごと。`id` は `con:kin:<rule.number>`、`label` は `rule.title`。
  - 世界一: `(ch, th_title)` の組ごと。`id` は `con:sekai:<ch>:<連番>`、`label` は `th_title`。連番は章内の出現順。
- **question**: 問題ごと。`id` は `q:<id>`、`label` は問題番号。親は、その問題が属する concept。
- **edges**: root → category → concept → question の `parent` のみ。
- ノード数の見込みは約 440(root 2、category 21、concept 約 117、question 301)。
- 出力は決定的にする(ソート順を固定し、同じ入力から常に同じ出力になる)。
- 金の文法の問題で `rule` が欠けている場合は、スクリプトを異常終了させる(黙って捨てない)。

## 4. 理解度の計算(`js/mastery.js`)

画面や `state` に依存しない**純粋関数**として書く。ブラウザでは `<script>` で読み込み、Node のテストからも読み込めるようにする(CommonJS と `window` の両対応の小さなラッパーで、ビルドは不要)。

### 入力

- `graph`: 上記の `GRAMMAR_GRAPH`。
- `stats`: `{ [qid]: { a, c } }`(既存の `grammarStats`)。
- `weak`: `{ [qid]: { streak, added, due } }`(既存の `grammarWeakData`)。
- `now`: 現在時刻(ms)。テストのために引数で受け取る。

### 出力

ノード ID をキーとする `{ [nodeId]: NodeState }`。

```js
NodeState = {
  total,      // 配下の問題数(重複なし)
  answered,   // 解答数の合計(stats.a の和)
  correct,    // 正解数の合計(stats.c の和)
  weak,       // 苦手に入っている問題数
  due,        // うち、いま復習の期限が来ている問題数
  rate,       // (correct + 1) / (answered + 2)。解答数が少ないとき 0.5 に寄せる
  state       // 'unseen' | 'few' | 'weak' | 'due' | 'mid' | 'good'
}
```

### `state` の決め方(上から順に判定)

定数は 1 か所にまとめ、調整できるようにする。

| 順 | 条件 | state | 表示 |
|---|---|---|---|
| 1 | `answered === 0` | `unseen` | 灰色 |
| 2 | `due > 0` | `due` | 赤 + 縁取り(強調) |
| 3 | `weak > 0` または `rate < 0.6`(かつ `answered >= 3`) | `weak` | 赤 |
| 4 | `answered < 3` | `few` | 薄い青 |
| 5 | `rate >= 0.8` かつ `weak === 0` | `good` | 緑 |
| 6 | それ以外 | `mid` | 黄 |

- 集計は、そのノードの配下の `question` すべてを対象にする。同じ問題が複数の経路から届いても、1 回しか数えない。
- `question` ノード自身も同じ規則で判定する(解答数 0 なら `unseen`、など)。
- 記録に無い問題 ID は、解答数 0 として扱う。
- `GRAMMAR_GRAPH` に存在しない問題 ID が `stats` / `weak` にあっても、エラーにせず無視する。

## 5. グラフビュー(`js/graph-view.js`)

### 公開インターフェース

`<script>` で読み込み、`window.GraphView` を 1 つだけ公開する。`index.html` の `state` には触れない。必要な値は呼び出し側から渡す。

```js
GraphView.mount(container, {
  graph,            // GRAMMAR_GRAPH
  getStats,         // () => grammarStats
  getWeak,          // () => grammarWeakData
  getQuestion       // (qid) => RAW_GRAMMAR の要素 (シート表示用)
});
GraphView.refresh();   // 記録が変わったとき、色だけ更新する
GraphView.destroy();   // 画面を離れるとき、物理シミュレーションを止める
```

「このノードを練習」のような出題への導線は、後続機能で足す。今回の公開インターフェースには含めない。

### 描画

- SVG。エッジは `<line>`、ノードは `<circle>`。ラベルはズームが一定以上のときだけ表示する。
- ノードの色は `state` から決める(4 節の表)。色はアプリのテーマ(`data-theme`)の CSS 変数を使い、既存のカラーテーマ切替に追従させる。
- ノードの半径は `kind` と配下の問題数で決める。`question` は小さな点にする。
- 表示の切り替え(情報量の制御):
  - 初期状態は root・category・concept を表示し、`question` は非表示にする。
  - ズームが閾値を超えたら `question` を表示する。間違えた問題は赤い点として見える。
  - 「苦手だけ」トグルで、`weak` / `due` のノードと、その祖先だけを残す。
  - 本(sekai / kin)による絞り込みトグルを置く。

### 物理配置

- `d3-force`(`forceSimulation`、`forceLink`、`forceManyBody`、`forceCenter`、`forceCollide`)を使う。
- `vendor/` に必要なファイル(d3-force、d3-dispatch、d3-quadtree、d3-timer)を**同梱**する。CDN は使わない。`sw.js` のキャッシュ対象に加える。
- 開いた直後に収束するまでの間、描画が重くならないようにする。シミュレーションが収まったら停止し、ドラッグしたときだけ再開する。
- 画面を離れたら必ずシミュレーションを止める(`destroy`)。

### 操作

- ドラッグ(ノード): ノードを動かし、つながるノードが追従する。
- ドラッグ(背景): パン。
- ピンチ・ホイール: ズーム。
- タップ: 下からシートを出す。シートの内容は次のとおり。
  - ノード名と本の名前
  - 状態、正答率、解答数、苦手の数
  - 配下の問題の一覧(問題文の先頭、正誤の状態)
- シートは `Esc` かシートの外側のタップで閉じる。
- スマホを基準にし、タップ領域は小さな点でも当てやすいように、見た目より広い透明な当たり判定を持たせる。

### 更新のタイミング

- 「グラフ」を開いたとき、`mastery` を計算して色を付ける。
- 他の画面で解答した後にグラフへ戻ったときも、開き直しで最新になる(常時監視はしない)。

## 6. `index.html` への統合

- 「学習対象」のセグメント(トップの `#app-type-segments` と、絞り込みシート内の `#sheet-app-type-segments`)に `data-app="graph"` の「グラフ」を追加する。
- `setApp('graph')` のとき: 単語・文法のフィルタ、モード切替、問題カード表示を隠し、グラフ用のコンテナを表示して `GraphView.mount` を呼ぶ。他の app へ切り替えるときは `GraphView.destroy()` を呼び、コンテナを隠す。
- 既存の `setApp('vocab' | 'grammar')` の動作(セッション復元、フィルタ適用)は変えない。
- `state.app` に `'graph'` を保存して次回起動で復元するかどうかは、起動を壊さないことを優先する。保存済みの `app` が `'graph'` の場合も、復元で例外を出さないこと。(実装計画で具体化する)
- `sw.js` の `ASSETS` に、`data/grammar_graph.js`、`js/mastery.js`、`js/graph-view.js`、`vendor/*` を追加する。
- `upload.py` の `FILES` に同じものを追加する。`tools/` と `docs/` と `tests/` はアプリの配信物ではないので含めない。

## 7. テスト

- `tests/mastery.test.js` を `node --test` で実行する。
  - 境界値: 解答数 0 / 2 / 3、`rate` が 0.6 と 0.8 の前後、`due` と `weak` の優先順位。
  - 集計: 同じ問題が複数経路から届く場合に二重に数えない。
  - 堅牢性: グラフに無い問題 ID が記録にある場合、記録に無い問題がグラフにある場合。
- `tests/build_graph.test.js`:
  - 生成したグラフが契約を満たす(ID の一意性、すべてのエッジの端点が存在する、すべての `question` に親がある)。
  - 全 301 問が漏れなく 1 回ずつ含まれる。
  - 生成が決定的である(2 回生成して同じ結果)。
- ブラウザでの確認(手動、または Playwright):
  - 「グラフ」を開いて描画される。
  - 苦手データがある状態で、該当ノードが赤になる。
  - ノードのタップでシートが開き、問題一覧が出る。
  - オフライン(Service Worker 経由)でも開く。
  - 他の app へ切り替えても、既存の動作に影響が無い。

## 8. 完成の基準

1. オフラインでグラフが開く。
2. 間違えた問題と苦手なノードが赤く表示される。
3. ノードをタップすると、正答率と紐づく問題が見える。
4. `mastery.js` と生成スクリプトのテストが通る。
5. スマホ幅で、約 440 ノードを動かしても引っかからない。
6. 既存の単語ドリル・文法ドリルの動作が変わらない。

## 9. リスクと未決事項

- **d3-force の同梱**: npm からの取得ができない場合は、同等の小さな力学シミュレーション(リンクのばね、反発、中心への引力)を自作して置き換える。ビューの公開インターフェースは変わらない。
- **グラフの契約が md の内容に合わない可能性**: md を受け取った時点で `kind` や `related` の扱いを見直す。契約を変えるときは `version` を上げる。
- **世界一の小テーマの粒度**: `th_title` の区切り(「A / B」のような複合ラベル)は、そのまま 1 つの concept として扱う。細分化は md の内容を見てから判断する。
- **`state.app = 'graph'` の保存と復元**: 6 節のとおり、実装計画で具体化する。
- **モジュール分割**: `js/` は新規コードのみ。既存の 5,000 行の `index.html` の分割は今回やらない。
