# 文法グラフビュー v2 設計（軽量版・文法4冊）

日付: 2026-11-08 / 状態: **§12 の確認事項は決定済み。設計書のレビュー待ち（承認後に実装計画へ）**

前の設計書（`2026-10-26-grammar-graph-view-foundation-design.md`）の後継。目的と読み方の考え方は引き継ぐが、
**描画と配置の方式を作り直す**。前の設計書は 301 問（金の文法・世界一）が前提で、SVG + d3-force の実行時シミュレーションだった。
今は文法が 4 冊 983 問に増え、アプリ全体を軽くする作業の途中なので、方式を変える。

## 1. 目的と範囲

- 目的: 解いた履歴が色で見え、**苦手な概念・ひっかけ（Trap）・ルール・問題**が串刺しで分かる。弱点の可視化が主で、出題の差し替えはしない。
- 範囲は **A: 文法だけ（4 冊 983 問）**。単語はこの設計に含めない（単語には概念・Trap にあたる元データがない）。
- 含む: グラフデータの生成（ビルド時）、座標の事前計算、理解度の計算（純粋関数）、描画（Canvas）、操作（パン・ズーム・タップ）、詳細シート、画面への入口。
- 含まない（後続）: 30 問診断、章チェック、グラフからの出題、練習ボタン、単語のグラフ、バックアップ形式の変更。
- 記録は**読むだけ**。新しい保存キーを作らない。

### 守ること（制約）

- 静的 HTML・ビルドなしのアプリのまま。ビルドが要るのは「データを作る手元のスクリプト」だけで、生成物をコミットする。
- オフラインで動く（`sw.js`）。スマホ幅が基準で、PC でも使える。
- **既存の単語ドリル・文法ドリルの動作と、起動時の読み込みを変えない**（§9 でテストする）。
- 既存の保存内容（golden テスト）を 1 バイトも変えない。

## 2. 軽さの方針（この版の核心）

2026-11-08 の調査（`docs/performance-investigation-2026-11-08.md`）で分かったこと:
CPU の計算量は問題にならず、効くのは**描画・アニメーションを動かし続けること、通信、不要な書き込み**。
グラフビューはこれに沿って次の 5 つを守る。

1. **座標は事前計算する。** ビルド時に d3-force（Node 上）で配置を計算し、座標を生成物に入れる。実行時の物理シミュレーションはしない。→ d3 をアプリに同梱しない（`vendor/` 不要）。
2. **画面を開いたときに読み込む。** グラフ用のデータとコードは起動時に読まない。`<script>` を動的に差し込む。→ 起動のリクエスト数・転送量は 1 バイトも増えない。
3. **Canvas 2D で描く。** SVG のように、ノード数だけ DOM 要素を持たない。
4. **動いていないときは何もしない。** パン・ズーム・タップなどの入力があったときだけ、`requestAnimationFrame` で 1 回描く（dirty フラグ）。タイマーなし、常時ループなし。画面を離れる・タブが hidden になったら、描画を止めて資源を解放する。
5. **見える範囲だけ描く。** 画面外のノード・エッジは描かない（ビューポートで間引く）。ズームに応じて LOD（段階表示）で描く数を絞り、ラベルは上限つきで描く。

### 3.2 対応づけの注意（実装の最初に必ず検証する）

Vault の問題とアプリの問題を結ぶ当初の想定は「Vault の `practice_id` = アプリの `id`」だったが、2026-11-08 の検証で**ID では結べない本がある**とわかった（結果は下の「検証結果」）。当初の確認にあった「983 問中 915 問が一致、68 問が不一致（すべて `toplevel`）」は、本を区別せずに数値だけを比べた誤りで、**撤回する**。

- **対処の方針（実装済み）**: ① 同じ本どうしで `id` = `practice_id` なら結ぶ → ② 問題文（`q`）を正規化（空白・記号・全半角・大文字小文字を揃える）した文字列が一致すれば結ぶ（OCR のごみによる包含も許す）→ ③ 本文が使えない本は、問題数が等しく並び順が一致する場合に限り並び順で結ぶ。それでも結べない問題は「概念なし」として入れ、**ビルドのログに件数と一覧を出す**。完成の基準は未対応 0 件（無理なら理由を設計書に書き足す）。
- `practice_id` の付き方は本ごとに違う（金 1001〜、トップレベル 2001〜2664、ポラリス 3001〜3415 など）。詳細は下の表。

#### 検証結果（2026-11-08、`node tools/check_mapping.mjs /Users/reiji/projects/English_study`）

本ごとに見ると、`practice_id` の付き方は次のとおりで、ID だけで結べるのは世界一と金の 301 問だけ。

| 本 | アプリ（`id`、問題数） | Vault（`practice_id`、問題数） | 結び方 |
|---|---|---|---|
| `sekai`（世界一） | 1〜141（141） | 1〜141（141） | ID 一致 141 |
| `kin`（金） | 1001〜1160（160） | 1001〜1160（160） | ID 一致 160 |
| `polaris2`（ポラリス） | 2001〜2334（334 連番） | **3001〜3415（334、欠番あり）** | 本文一致 63 + 並び順 271 |
| `toplevel`（トップレベル） | 3001〜3348（348 連番、重複除去後に振り直し） | **2001〜2664（664）** | 本文一致 348 |

- ポラリスとトップレベルは、アプリと Vault で **千の位が入れ替わっている**（アプリのポラリス 2xxx は Vault のトップレベル 2xxx と同じ番号）。ID の数値だけで結ぶと別の本の問題に誤って結ぶ。**ID 一致は「同じ本」のときだけ有効**にした。
- 結果は **対応済み 983 問・未対応 0 問**（ID 一致 301 / 本文一致 411 / 並び順 271 / 未対応 0）。
- トップレベル 348 問はすべて本文一致で結べた（章の一致も 348/348）。Vault 側の本文は、引用ブロックの次の行に英文が続く形式、定型の指示文（「空欄に入る最も適切なものを選びなさい。」）、教材 PDF のフッター（`© RECRUIT HOLDINGS …`）、1 行にまとめた選択肢が混ざるため、これらを除き、さらに「どちらかがもう一方に含まれる」ことを許して結んだ。Vault の同文重複（123 組）は同じ本の未使用のものを `practice_id` 順に割り当てた。重複どうしで概念・Trap のリンクが違うのは 3 組だけで、影響は小さい。
- ポラリスは Vault 334 問のうち **131 問の本文が「Polaris Question N」という仮の文字列**で、OCR の雑音が付いた本文も多く、本文では 65 問しか結べない。一方で **アプリのポラリスは Vault のポラリス 334 問と同数で、並び順も同じ**（本文で結べた 65 問のうち 63 問は「アプリの何番目 = Vault の何番目」が一致し、残り 2 問は同文の重複を取り違えただけ）。そこで「問題数が等しく、本文で結べた組の 9 割以上が並び順と一致する本」に限り、その本の全問を並び順（`id` 順 = `practice_id` 順）で結んだ（本文一致 63 + 並び順 271 = 334。同文の重複を取り違えた 2 問も並び順で結び直した）。結んだ 334 問は章（`ch`）がすべて Vault の `chapter` と一致した。
- 原因（推定）: アプリのポラリスは Vault の全 334 問をそのまま取り込み番号だけ振り直したもの、トップレベルは Vault 664 問から重複・形式外を除いた 348 問に絞って振り直したもの、と推定される（件数・並び順・本文の一致と矛盾しないが、振り直しの経緯そのものは確かめていない）。
- 概念リンク 2,116 本・Trap リンク 257 本はすべて実在する `00_Concepts` / `04_Traps` を指していた（リンク切れ 0）。概念を持たない問題も 0 問。
- ポラリスの並び順による対応 271 問は、本文（Vault 側が仮の文字列）では裏づけられない。**検証は章番号による**: Vault の問題ノートの `chapter` とアプリの `ch` を比べ、並び順で結ぶ組に食い違いが 1 組でもあればその本には並び順を使わない（コードで強制。`tools/lib/match.mjs`）。実 Vault では 271 組すべて章が一致した（`check_mapping.mjs` が「並び順で結んだ組の章の確認」として毎回出力し、食い違いがあれば失敗する）。並び順を使う条件は、問題数が等しいこと・本文または ID で結べた組が 5 組以上で 9 割以上が順位どおりであること（本文で結べた 65 組のうち 63 組が順位どおり）、ID 一致の組は上書きしないこと。ビルドのログには `order` で結んだ件数を出し続けること。

## 4. グラフの形

### 4.1 ノード

| kind | 件数の目安 | 内容 |
|---|---|---|
| `book` | 4 | 本。アプリの `GRAMMAR_BOOKS`（`js/grammar-drill.js`）の識別子・名前に合わせる |
| `chapter` | 51 | 章。`ch_title` |
| `rule` | 約 460 | ルール。`rule.number`（`rule.title`）で本ごとに数える（金 82 など）。世界一は `rule` を持たないので `(ch, th_title)` の組（38）で代用 |
| `concept` | 13 | 普遍概念。`desc`（要約）つき |
| `trap` | 12 | ひっかけ。`desc`・`advice` つき |
| `question` | 983 | 問題 |

合計は約 1,500 ノード、エッジは約 3,300 本（親子 約 1,500 + 概念 約 1,600 + Trap 約 190）の見積もり（実装時に確定）。

**ルールの粒度に注意**: 金の文法とポラリス 2 は、`th_title` が問題ごとにほぼ別の文字列になる（金は 160 問で 160 通り）。ルールを `th_title` で作ると 1 問 1 ルールになってしまうので、`rule.number` を使う。

### 4.2 エッジ

- `parent`: book → chapter → rule → question（金の文法でルールが複数の章にまたがる場合は、親 chapter エッジが複数）。
- `concept`: question → concept（1 問に複数あり）。
- `trap`: question → trap。

### 4.3 生成物 `data/grammar_graph.js` の形（軽さ優先）

オブジェクトの配列ではなく、**列ごとの配列（struct of arrays）**にして、サイズとパースの時間を抑える。

```js
const GRAMMAR_GRAPH = {
  version: 3,
  kinds: ['book','chapter','rule','concept','trap','question'],
  // ノード（同じ添字が 1 ノード）
  id:    [...],   // 文字列。全体で一意（例: 'book:kin', 'rule:kin:30', 'con:受動態', 'q:123'）
  kind:  [...],   // kinds の添字
  label: [...],   // 表示名（question は問題番号などの短いもの）
  x:     [...],   // 事前計算した座標（整数に丸める）
  y:     [...],
  qid:   [...],   // question のみアプリの問題 id、それ以外は 0
  // エッジ: [始点の添字, 終点の添字, 種類(0 parent / 1 concept / 2 trap)] を平らに並べる
  edges: [...],
  // 解説文（concept / trap のみ。ノードの添字をキー）
  text:  { 123: { desc, advice }, ... },
};
```

- 子孫の問題の集計を速くするため、**各ノードの配下の問題 id 一覧**（または、問題を並べた配列と、各ノードの区間 `[from, to)`）もビルド時に作って入れる。実行時にグラフを辿り直さない。
- サイズの目安: 数百 KB 以内（gzip 後はもっと小さい）。実装時に実測し、超えるなら座標・エッジの符号化を見直す。

## 5. 事前計算する配置（`tools/build_grammar_graph.mjs`）

- 手元で `node tools/build_grammar_graph.mjs` を実行し、`data/grammar_graph.js` を作ってコミットする。入力は `RAW_GRAMMAR` と、Vault のパス（引数または環境変数。Vault はリポジトリの外にある）。
- 配置は **Node 上の d3-force**（`forceLink` / `forceManyBody` / `forceCenter` / `forceCollide`）。ツールの依存であって、アプリには含めない。
  - 乱数を固定（`simulation.randomSource` に種つきの乱数）し、tick 数も固定する → **同じ入力から同じ出力**になる（テストで確かめる）。
  - 親子エッジは強く、概念・Trap のエッジは弱く結ぶ。概念・Trap は本をまたぐハブなので、中央寄りに集まり、本ごとの塊の間をつなぐ形になる想定。
  - ノードの種類ごとの半径で衝突を避ける。
  - 座標は整数に丸めて出力する。
- 配置の見た目の良し悪しは、実装中にスクリーンショットで確認し、力の係数を調整する（調整は生成スクリプトの定数にまとめる）。
- npm の依存（d3-force 3.0.0 とその依存）が必要になる。`tools/` に `package.json` を置いて入れる（この Mac に Node 22 はある）。何を入れたかは作業の最後に報告する。アプリの `upload.py` の公開対象にも、テスト（`tests/`）の対象にも `node_modules` は含めない。

## 6. 理解度の計算（`js/mastery.js`）

前の設計書の考えをそのまま使う。画面や `state` に依存しない**純粋関数**で、Node のテストからも読み込める（CommonJS と `window` の両対応の小さなラッパー）。

### 入力と出力

- 入力: グラフ、`stats`（`{ [qid]: { a, c } }`、既存の `grammarStats`）、`weak`（既存の `grammarWeakData`。現行の形は実装時に `js/word-stats.js`・`js/grammar-drill.js` で確認する）、`now`（テストのため引数）。
- 出力: ノードごとの `{ total, answered, correct, weak, due, rate, state }`。`rate = (correct + 1) / (answered + 2)`。

### `state` の決め方（上から判定。定数は 1 か所にまとめる）

| 順 | 条件 | state | 表示 |
|---|---|---|---|
| 1 | `answered === 0` | `unseen` | 灰 |
| 2 | `due > 0` | `due` | 赤 + 縁取り |
| 3 | `weak > 0` または（`answered >= 3` かつ `rate < 0.6`） | `weak` | 赤 |
| 4 | `answered < 3` | `few` | 薄い青 |
| 5 | `rate >= 0.8` かつ `weak === 0` | `good` | 緑 |
| 6 | それ以外 | `mid` | 黄 |

- 配下の問題（直接と子孫）を、重複なく 1 回ずつ数える。記録にない問題は解答数 0。グラフにない問題 id の記録は無視する（エラーにしない）。
- **速さ**: 983 問に対し、問題ごとの値を平らな配列（`Int32Array`）に 1 回だけ作り、各ノードは区間の和で求める。計算は画面を開いたときと、`refresh` のときだけ。

## 7. 描画と操作（`js/graph-view.js`）

### 公開インターフェース

`window.GraphView` を 1 つだけ公開し、`state` には触れない。必要な値は呼び出し側から渡す。

```js
GraphView.mount(container, { graph, getStats, getWeak, getQuestion });
GraphView.refresh();   // 記録が変わったとき、色だけ更新する（再描画を 1 回要求）
GraphView.destroy();   // 画面を離れるとき。リスナー・rAF・Canvas を解放
```

### Canvas の描き方

- `<canvas>` 1 枚。`devicePixelRatio` は上限 2 に抑える。
- ノードの形は前の設計書を引き継ぐ: `concept` は二重リング、`trap` は破線、`book` > `chapter` > `rule` > `question` の順に小さく。色は `state`（§6）を、テーマ（`data-theme`）の CSS 変数から読み取る（描画時に `getComputedStyle` を毎回呼ばず、マウント時とテーマ変更時に読み取って保持する）。
- エッジは種類ごとにまとめて 1 つの path で描く（親子は実線の薄い灰、概念は点線、Trap は破線の警告色）。
- ビューポート外のノード・エッジは描かない。

### LOD（段階表示）

| ズーム | 描くもの |
|---|---|
| 遠景 | `book`, `concept`, `trap`, `chapter` |
| 中景 | + `rule` |
| 近景 | + `question` |

- ラベルは、画面に入っていて、かつ重ならない範囲だけ、上限つき（目安 80 個）で描く。

### 操作

- ドラッグ（背景）でパン、ホイール / ピンチでズーム（Pointer Events を使い、2 本指のピンチも扱う）。**ノードのドラッグ移動はしない**（座標は固定）。
- タップは**当たり判定を格子索引で引く**（ビルド時、または mount 時に座標から作る）。全ノードの総当たりはしない。当たり判定は見た目より大きめにとる。
- 絞り込み: 「すべて / 金 / 世界一 / ポラリス2 / トップレベル」、「苦手のみ」トグル（`weak` / `due` のノードとつながる先だけ）。純粋関数 `js/graph-filter.js` にして Node でテストする。
- 描画は入力があったときだけ。慣性スクロールのアニメーションは、まずは入れない（入れるなら終わったら必ず止める）。

### 詳細シート

タップしたノードの種類に応じた見出し、状態・正答率・解答数・苦手数、concept / trap は `desc` と `advice`、配下の問題一覧（問題文の先頭と正誤の状態）を出す。既存のシート部品（`.bottom-sheet`）を再利用できるか、実装時に確かめる。`getQuestion(qid)` は `RAW_GRAMMAR` を引く（起動時から読み込まれている）。シートは外側のタップ・Esc で閉じる。

## 8. 画面への入口

現行の画面は下部ナビ（ホーム・演習・復習・集中・設定の 5 タブ。`index.html` の `.top-page-tabs`、`home.js` の `switchAppPage` と `APP_PAGES`）で、前の設計書が前提にした「学習対象のセグメント」への追加とは構造が変わっている。

- **PC 幅（1000px 以上）**: 左サイドバーの `.top-page-tabs` に「グラフ」タブを足す（§12 #6）。縦に並ぶので窮屈にならない。`APP_PAGES` に `graph` を足す形か、タブから `graph-page` を開く形かは、`home.js` の `switchAppPage` を見て実装計画で決める。
- **推奨（スマホ幅）**: 6 つ目のタブは増やさない（スマホ幅で窮屈になる）。**ホームまたは復習ページにカードを置き、全画面の `graph-page` を開く**。戻るボタンで元のページへ戻る。ハッシュ（`#graph`）で直接開けるようにするかは、既存のハッシュ処理（`home.js`）を見て決める。
- 開いたとき: 読み込み中表示 → グラフ用の `<script>`（`data/grammar_graph.js`、`js/mastery.js`、`js/graph-filter.js`、`js/graph-view.js`）を順に差し込む → `GraphView.mount`。読み込みに失敗したら（オフラインで未キャッシュなど）理由と再試行を出す。
- 閉じたとき: `GraphView.destroy()`。
